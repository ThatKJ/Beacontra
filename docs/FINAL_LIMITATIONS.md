# Beacontra Final Limitations

## FIXED LIMITATIONS
- **Demo Latency:** The initial 112-second live scan latency was resolved by parallelizing up to 10 Lens API calls concurrently, dramatically reducing total response time to ~15 seconds.
- **Reference Image File Upload:** Upgraded the UI and API to natively support standard browser file uploads using `multipart/form-data`, passing image binaries directly to SerpApi for reverse lookup, eliminating the requirement to manually host reference images.
- **Variant Skew and False Positives:** Hardened Shopping result normalization with deterministic regex variant extraction (e.g., distinguishing "boAt Airdopes 141" from "Elite ANC", "Pro", and "cases"), ensuring prices are compared against matching SKUs.
- **Price Anomaly Granularity:** Overhauled the price signal logic to distinguish `below_mrp` (extreme deviation <50%), `large_deviation` (<70%), and `moderate_discount` (<90%), stopping ordinary market discounts from dominating review priority. **Caveat (see below):** this granularity only helps when the *reference* price is realistic. When printed MRP itself is heavily inflated relative to genuine street price — common for Indian consumer electronics, and true of the canonical demo product — every real listing still lands in the same `below_mrp` bucket regardless of this fix.
- **Seller Signal Penalties:** Fixed a logic bug where `no_authorized_list` penalized the score by 15 points. It now provides a neutral 5-point baseline, ensuring unknown sellers are not automatically presumed fraudulent without an explicit brand allowlist.
- **Error Transparency:** Extracted backend SerpApi status errors into the frontend UI, replacing generic connection failures with actionable error messages.
- **Lens Coverage Explanation:** Added clear provenance messaging to the UI explicitly stating that visual analysis is bounded to the top 10 most anomalous candidates to respect API quotas.

## UNAVOIDABLE (OR KNOWN/ACCEPTABLE) LIMITATIONS
- **Live Search Variability:** As Beacontra pulls live data, search results and exact rankings for the same product can shift over time depending on Google's Shopping index.
- **Lens Visual Evidence Caps:** To safely manage SerpApi credits, visual analysis is inherently restricted to the top 10 candidate listings. The remaining listings are classified as `not_verified` but retain their commercial price/seller evidence.
- **Absence of Visual Evidence:** Google Lens often returns no exact product matches for typical e-commerce thumbnail images, degrading the visual signal to `no_evidence` or `unavailable`. This is accepted as a natural limitation of third-party indexes and Beacontra falls back gracefully to commercial signals rather than making false claims.
- **Score Subjectivity:** The Review Priority Score is a hand-tuned deterministic heuristic, not a machine-learned probability or legal guarantee of counterfeit status.
- **MRP-vs-street-price miscalibration (found this session, verified against the canonical run, not assumed):** `docs/FINAL_VERIFIED_RUN.md`'s own price-signal table shows **11/11 (100%)** of the canonical run's results landed in the most severe `below_mrp` bucket — not `large_deviation` or `moderate_discount`. That doc's own text explains why: boAt Airdopes 141's printed MRP is ₹4,490, but it "legitimately retails around ₹1,299-₹1,499 across Indian marketplaces" — a ~70% discount off MRP that is *normal, fully-legitimate pricing for this product*, not evidence of anything. `analyzePrice()` (`src/lib/beacontra.ts`) computes its buckets purely as a percentage of the raw `mrp` input, so in any category where printed MRP is conventionally inflated relative to genuine online price (common for Indian consumer electronics), the price signal cannot discriminate a suspicious listing from a completely normal, fully-authorized one — everything lands in the same maximally-alarming bucket. The composite score still relies on price+seller+visual fusion rather than price alone, so this doesn't make the tool useless, but the price axis specifically contributes little discriminating power for this exact demo product, and the "PASS" verdict in `docs/FINAL_VERIFIED_RUN.md` doesn't currently say so. `BeacontraInput.expectedPriceRange` already exists as a more realistic alternative baseline (a genuine typical-price band rather than printed MRP) but `analyzePrice()` only consults it when `mrp` is entirely absent — if both are supplied, the less-discriminating MRP buckets take priority unconditionally. Not fixed this session (a threshold/precedence change affects scoring, which is OPENCODE's owned surface per the coordination protocol); flagging here so the demo narrative doesn't imply the price signal cleanly separates suspicious from normal for this specific product, and so whoever picks this up next has the precedence fix already scoped.
